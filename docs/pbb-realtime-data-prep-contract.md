# PBB Realtime Data Prep Contract

## Purpose

Realtime participates in Kit Setup's standalone Data Prep workflow. Data Prep is separate from normal Setup install. Setup installs the app, starts infrastructure services, and runs smoke checks; Data Prep prepares app-owned records, applies app-to-app settings, and verifies the prepared state.

Current Realtime Data Prep scope:

- prepare the PBB Hotline Realtime client profile
- prepare Hotline policies for media ingest, broadcast, citizen, operator, and command
- prepare Hotline project scopes for server, citizen, operator, and command
- apply Maestro telemetry settings generated by Kit
- verify Hotline records and Maestro telemetry settings without exposing secrets

## Release Metadata

`release.json` declares:

- `data_prep.version=1`
- `data_prep.capabilities.prepare_data=true`
- `data_prep.capabilities.apply_settings=true`
- `data_prep.capabilities.verify=true`

Tools:

- `prepare_data`: `tools/populate-initial-data.php`
- `apply_settings`: `tools/data-prep/apply-settings.php`
- `verify`: `tools/data-prep/verify.php`

All tools use the common CLI shape:

```powershell
C:/wamp64/bin/php/php8.2.29/php.exe <tool> --mode initial --config <config.json> --report <report.json> [--dry-run]
```

Supported modes remain app-tool modes: `initial`, `repair`, `refresh`, and `demo`. Data Prep is the Kit workflow name, not a mode value.

## Prepare Data

`tools/populate-initial-data.php` imports Realtime client records from:

1. `realtime.populate.source`, when supplied
2. `realtime.populate.clients`, when supplied
3. packaged default source `resources/data/realtime/hotline-client-data.json` when no explicit source or client array is configured

The packaged Hotline source contains:

- 1 client: `clt_PBB_HOTLINE`
- 5 policies:
  - `pol_HOTLINE_MEDIA_INGEST`
  - `pol_HOTLINE_BROADCAST`
  - `pol_HOTLINE_CITIZEN`
  - `pol_HOTLINE_OPERATOR`
  - `pol_HOTLINE_COMMAND`
- 4 project scopes:
  - `prj_HOTLINE_SERVER`
  - `prj_HOTLINE_CITIZEN`
  - `prj_HOTLINE_OPERATOR`
  - `prj_HOTLINE_COMMAND`

The packaged source intentionally does not include raw backend ingress secrets, demo sessions, or audit rows.

## Apply Settings

`tools/data-prep/apply-settings.php` persists Maestro telemetry settings for Realtime through `RealtimeRuntimeSettings::updateMaestroTelemetry()`. Values are stored in `realtime_runtime_settings`, where `setting_value` is encrypted by the model cast. The same tool can also apply TLS trust settings to project-scoped media ingest routes after Prepare Data has created the Hotline projects.

Expected Kit config:

```json
{
  "realtime": {
    "data_prep": {
      "apply_settings": {
        "maestro": {
          "enabled": true,
          "base_url": "https://maestro.pbb.ph",
          "app_code": "realtime",
          "telemetry_token": "<plain run-scoped token>",
          "tls_verify": true,
          "ca_bundle": "C:/path/to/cacert.pem",
          "connect_timeout_seconds": 3,
          "timeout_seconds": 5
        },
        "media_ingest": {
          "enabled": true,
          "project_codes": [
            "prj_HOTLINE_SERVER",
            "prj_HOTLINE_CITIZEN",
            "prj_HOTLINE_OPERATOR"
          ],
          "base_url": "https://hotline.pbb.ph",
          "tls_verify": true,
          "ca_bundle": "C:/path/to/cacert.pem"
        }
      }
    }
  }
}
```

Token fallback keys are also accepted from `secrets.values.maestro_realtime_telemetry_token` or `secrets.values.realtime_maestro_telemetry_token`.

CA bundle aliases for Maestro telemetry and media ingest:

- `ca_bundle`
- `curl_ca_bundle`
- `ssl_cert_file`

Reports are secret-safe. They expose `token_supplied`, `secret_refs`, `tls_verify`, and `ca_bundle_configured`, but never the raw telemetry token.

## Verify

`tools/data-prep/verify.php` checks:

- Hotline client exists
- all 5 Hotline policies exist
- all 4 Hotline project scopes exist
- Maestro telemetry settings exist when Maestro apply/verify config is present
- media ingest project routes have a CA bundle when media ingest apply/verify config is present

Maestro telemetry verification confirms:

- `maestro_telemetry_enabled`
- `maestro_base_url`
- `maestro_telemetry_app_code`
- `maestro_telemetry_token` is configured
- `maestro_telemetry_ca_bundle` is configured when Kit supplied a CA bundle

The Realtime verifier does not query Maestro heartbeat freshness. Heartbeat freshness is verified by Maestro's own Data Prep verify tool after Kit restarts or waits for client services.

## Runtime Services And Heartbeats

Realtime declares two Kit-managed runtime services:

- `pbb-realtime-websocket`
  - command: `php artisan realtime:serve`
  - role in Maestro telemetry: `websocket-gateway`
  - required for smoke
- `pbb-realtime-media-dispatcher`
  - command: `php artisan realtime:dispatch`
  - role in Maestro telemetry: `media-chunk-dispatcher`

Both services emit Maestro worker events and heartbeats through `RealtimeProcessTelemetry`.

The telemetry client reads `RealtimeRuntimeSettings::maestroTelemetry()` on each send, so DB-backed settings can be picked up without a process restart. For the cleanest Data Prep Verify flow, Kit may restart both Realtime services after Apply Settings so Maestro receives fresh `worker.started` and heartbeat records immediately.

## TLS Trust

Realtime telemetry uses Guzzle/Laravel HTTP to reach Maestro. On Windows hosts, PHP/cURL may not trust the local HTTPS certificate chain by default. Kit should pass its trusted CA bundle path to Realtime Data Prep Apply Settings:

```json
{
  "realtime": {
    "data_prep": {
      "apply_settings": {
        "maestro": {
          "tls_verify": true,
          "ca_bundle": "C:/wamp64/www/pbb/kit-setup/assets/certs/cacert.pem"
        }
      }
    }
  }
}
```

Realtime persists that path as `maestro_telemetry_ca_bundle` and passes it to Guzzle as the `verify` option. Avoid disabling TLS verification except as a controlled local setup fallback.

Realtime media chunk forwarding also uses Laravel HTTP/Guzzle. For Hotline ingest over `https://hotline.pbb.ph`, Kit should pass the same trusted CA bundle through Data Prep Apply Settings:

```json
{
  "realtime": {
    "data_prep": {
      "apply_settings": {
        "media_ingest": {
          "project_codes": [
            "prj_HOTLINE_SERVER",
            "prj_HOTLINE_CITIZEN",
            "prj_HOTLINE_OPERATOR"
          ],
          "base_url": "https://hotline.pbb.ph",
          "tls_verify": true,
          "ca_bundle": "C:/wamp64/www/pbb/kit-setup/assets/certs/cacert.pem"
        }
      }
    }
  }
}
```

Realtime persists that path in each matching project's `media_ingest_settings.ca_bundle` and passes it to Guzzle as the `verify` option. Do not disable TLS verification for production media ingest.

## Bundle Handoff

Any Data Prep metadata, tool, source, report, checksum, or docs change must be shipped through the canonical bundle:

```text
pbb-realtime-1.0.0.zip
```

After changes:

1. refresh `checksums.sha256`
2. build `storage/app/installer-build/pbb-realtime-1.0.0.zip`
3. copy the canonical ZIP to Kit's trusted package path
4. update Kit `packages.bundled.json` with the new SHA-256
5. have Kit rebuild `setup.exe`

Do not hand Kit suffix bundles such as `-data-prep`, `-fixed`, `-test`, or `-hotfix`.
