# PBB Realtime Client And Project Scope Split Proposal

## Purpose

Define a cleaner administrative model for `PBB Realtime` where one trusted client can support multiple PBB projects or scopes without overloading a single record.

This proposal exists because the current client profile is starting to mix two different concepts:

- the trusted integration identity
- the per-project policy and browser access scope

That coupling is workable for a single project, but it becomes hard to manage when one client must serve more than one PBB app.

## Problem Statement

The current client model carries fields for:

- trust identity
- token issuance mode
- signing profile
- allowed origins
- policy references
- room/capability references
- project code

That means a single client record is doing two jobs at once:

1. identifying who is trusted
2. defining where and how that trust applies

For a one-project client, that is simple.

For a multi-project client, it creates friction:

- one `project_code` is too narrow
- changing policy for one project risks affecting all others
- the profile becomes long and harder to reason about
- the operator UI becomes cluttered and error-prone

## Proposal

Split the current model into two related concepts:

- `RealtimeClient` as the trust and integration anchor
- `RealtimeProject` as the per-project policy and browser-access scope

The relationship should be:

- one client
- many project scopes

This keeps the trust root stable while allowing each project to have its own rules.

As part of the split, the operator-facing create/edit experience should stay intentionally small:

- client, project, and policy codes should be generated by the system
- the onboarding forms should only expose the fields needed to establish trust and basic routing
- advanced policy or metadata fields should be inherited from templates or preserved behind the scenes unless an operator explicitly needs to override them

## Conceptual Responsibilities

### Client

The client should answer:

- who is trusted
- which issuer identity is associated with that trust
- which signing profile is used
- how tokens are issued in principle
- who owns the integration
- whether the integration is active, quarantined, or inactive
- the client code and project code should be generated automatically, not typed by operators

In other words, the client is the root trust anchor.

### Project Scope

The project scope should answer:

- which PBB project this client applies to
- which origins are allowed for that project
- which policy profile applies
- which capability profile applies
- which room policy profile applies
- whether that project scope is active or restricted
- the project code should be generated automatically, not typed by operators

In other words, the project scope is the per-app policy boundary.

## Recommended V1 Field Split

### Fields That Should Stay On `RealtimeClient`

Recommended:

- `client_code`
- `name`
- `status`
- `integration_owner`
- `issuer_identity`
- `token_issuance_mode`
- `trusted_signing_profile`
- `trust_notes`
- `integration_notes`

Optional:

- a general-purpose description of the client trust relationship
- review metadata such as `last_reviewed_at`

### Fields That Should Move To `RealtimeClientProjectScope`

Recommended:

- `project_code`
- `allowed_origins`
- `origin_policy_mode`
- `policy_profile_code`
- `capability_profile_code`
- `room_policy_profile_code`
- scope-specific status
- scope-specific notes

### Naming And Ownership Decisions

The following decisions are now part of the proposal:

- new table name: `realtime_projects`
- a client may exist without any scopes: `yes`
- a scope may be shared by more than one client: `no`
- project scope status can override client status: `no`
- policy references live only on the scope: `yes`

That means the project model should be a first-class table, not a nested JSON blob and not an alias for the client record.

Each project scope belongs to exactly one client.

Each client may have zero or more project scopes.

## Suggested Scope Statuses

The project scope should have its own operational state, independent of the parent client where needed.

Recommended statuses:

- `active`
- `inactive`
- `quarantined`
- `pending`

This allows the client to remain trusted while one project scope is paused or restricted.

## Why This Is Better

This split gives `PBB Realtime` a cleaner administrative structure.

Benefits:

- one trust anchor can support multiple projects
- project-specific rules become easier to manage
- changes are less likely to leak across projects
- the admin UI can show client trust separately from project scopes
- future policy growth stays organized

## UI Implications

The admin surface should evolve from a single long client form into:

- a client detail page for trust and ownership
- a project scope list under that client
- a project scope modal launched from that client context for per-project rules

Project scopes should not be treated as a separate top-level browsing surface in the primary admin navigation.

This makes the operator experience more readable.

Instead of one overwhelming record, the UI becomes:

- client first
- client-owned policy second
- project scope second

The client detail page should therefore become the primary management surface for:

- trust
- client-owned policies
- client-owned project scopes

## Data Model Implications

This proposal does not require changing the meaning of `PBB Realtime` trust policy.

It does require making the boundary explicit:

- client records are about trust
- scope records are about application

That means a future migration could:

- keep existing client records
- move the project-specific fields into a new scope table
- seed a default scope for existing single-project clients

## Migration Strategy

Recommended migration path:

1. keep the current client data intact
2. introduce a new `realtime_projects` model/table
3. copy current project-specific fields into one default project row per client where applicable
4. update the admin surface to edit client trust and project scope separately
5. keep backward compatibility during the transition

## Recommendation

Proceed with the split.

The current model is good enough for a single PBB project, but it will become awkward as soon as one trusted client needs to serve multiple projects.

`RealtimeClient` should become the trust anchor.

`RealtimeProject` should carry the per-project policy and browser access rules.
