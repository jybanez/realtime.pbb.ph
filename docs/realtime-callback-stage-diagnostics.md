# Callback stage diagnostics

Reviewable source change only; not deployed. Session 64 showed 37.747 seconds before citizen onOpen while 13 serialized operator signaling callbacks consumed 29.610 seconds. Existing diagnostics did not identify the expensive inner operation, and the host sampler ended before the call. These observations are not a complete causal explanation.

With `REALTIME_GATEWAY_TIMING_ENABLED=true` at gateway startup, signaling callback logs now distinguish `signal.authorize`, `signal.fanout`, `signal.metrics`, `signal.usage`, `signal.session.touch`, `ack.send`, response cache lookup/write and cached replay. Fanout records count connection sends; ACK records still indicate handing bytes to the server connection, not confirmed browser receipt. Signal subtype uses a fixed enum; optional top-level correlation ID and request ID/type/room are bounded to 160 UTF-8 bytes. SDP, candidates, meta_json, event data, tokens and SQL bindings are excluded. Envelope request ID remains the reliable correlation key when a client supplies no correlation_id.

Each timing includes process-local span_id and parent_span_id. Child callbacks inherit the active request context. SQL count, elapsed sum, maximum and a fixed operation-count map aggregate only while a callback is active. SQL aggregates are inclusive: a query in a child is also counted in its parent. Never add parent and child SQL totals or parent and child elapsed durations. No individual SQL text or binding is retained or logged; aggregate storage is bounded by the current synchronous stack, not query volume. The old per-query console-loop listener is replaced by callback aggregates.

`measured_child_ms` sums directly nested measured callback durations; `unaccounted_ms` is parent elapsed minus that sum. It is not CPU time and does not identify a wait. It includes uninstrumented work, gaps and diagnostic overhead. Child log writes occur after the child's measured interval and remain in the parent's unaccounted interval. SQL elapsed can include driver/server/transport work; operation counts do not identify tables or locks. Failed query attempts that never emit QueryExecuted are not included. Exceptions unwind callback frames in finally so later requests cannot inherit prior context or SQL totals.

Detailed stage logs and SQL collection are opt-in; normal authorization, validation, duplicate response behavior, fanout, persistence and ACK order are unchanged. Existing one-second callback/loop warnings remain with tracing off. No timeout, retry, routing, media or admission change is part of this patch.

Signal subtype is now a fixed allowlist of the Hotline protocol values (ready, hangup, disconnect-request, hangup-confirm, hangup-complete, heartbeat, browser-offline, browser-online, video-state, caller-location, offer, answer, ice-candidate). Unknown values log only `other`, without altering the published signal or its authorization. SQL operation elapsed sums use the same fixed SELECT/INSERT/UPDATE/DELETE/OTHER categories as counts.

The earliest observable arrival at this application layer is entry to Ratchet `onOpen`, recorded as `socket.open.received_at`. Ratchet has already performed the HTTP upgrade before invoking this gateway callback. It does not expose original TCP accept, proxy arrival, upgrade request receipt or queue-enqueue times here. The parsed HTTP request is not evidence of those timestamps. Measuring those boundaries requires separate transport/proxy instrumentation; this patch makes no inferred arrival timestamp. Browser start-to-onOpen includes all preceding scheduling/transport/upgrade work, and cannot allocate those causes. ACK-send logs measure a connection send call, not socket flush or browser receipt.

Synthetic observer benchmark: run `php tests/benchmarks/callback-diagnostics.php`, using 5 rounds of 1,000 modeled requests, 8 child stages and 8 QueryExecuted events each, with a private temporary Monolog disk file removed afterward. On this Windows/PHP8.2.29 host the final run measured median per request off0.000031ms, aggregate0.043863ms (range0.024720–0.058131ms), aggregate plus 9 disk logs0.676402ms (range0.363431–0.685390ms). These measure observer mechanics only, not actual gateway/DB/network performance or live capture overhead. Real log target, stack depth and contention can change cost. No live traffic, database or application logs are used by the benchmark.

Review this exact revision before deploying. Enable only for an agreed bounded capture outside active calls, confirm loaded diagnostics with actual permitted traffic, preserve source/process/settings interventions and disable tracing afterward via an idle-window cache refresh/restart. The next real call needs independent upgrade/accept arrival timing and a reliable low-overhead host/DB observer to distinguish pre-onOpen waiting from gateway work. No automatic call or replay is authorized by this diagnostic document.
