# PBB Realtime Client Management Spec

## Purpose

Define the V1 client-registration, trust-metadata, and policy-reference model for `PBB Realtime`.

This spec is part of the private admin surface described in:

- `docs/pbb-realtime-admin-surface-proposal.md`
- `docs/pbb-realtime-proposal.md`
- `docs/pbb-realtime-token-and-auth-spec.md`

This spec is intentionally narrow. It focuses on the records and workflows needed to decide:

- which PBB apps may use `PBB Realtime`
- which issuer or trust metadata applies to each client
- which origins are allowed
- which client policies are active
- who owns the integration

It does not define:

- websocket transport behavior
- room authorization rules
- presence semantics
- chat or signaling payloads
- raw signing-key custody
- browser-visible secret distribution

Note:

- this document describes the current client-management shape
- if the client/project split proposal is adopted, the project-specific fields in this spec should move into `realtime_projects`
- the client record should remain the trust anchor
- operator-facing create/edit forms should stay minimal and should not require manual code entry for identity fields

## Scope

The client-management surface should support:

- client registration
- client edit and review
- client activation and disablement
- trust metadata tracking
- allowed-origin tracking
- token-issuance mode tracking
- integration notes and ownership metadata
- audit visibility for changes

The client-management surface should not become a general-purpose app registry, CRM, or secret manager.

## Core Concept

In `PBB Realtime`, a "client" is the platform record that represents one consuming PBB app or integration.

Each client record should answer:

- what app is this
- who owns it
- whether it is allowed to connect
- which issuer/trust metadata applies
- how the client should be treated operationally

Project-specific browser access, origin allowlists, and policy references belong to `realtime_projects`, not the root client record.

## Recommended V1 Fields

### Identity

Required:

- `client_code`
- `name`
- `status`

Recommended:

- `description`
- `integration_owner`
- `integration_notes`

### Trust Metadata

Required:

- `issuer_identity`
- `token_issuance_mode`

Recommended:

- `trusted_signing_profile`
- `trust_notes`

The trust metadata is descriptive and policy-oriented.

It should not expose raw signing secrets.

### Origin Policy

Recommended:

- `allowed_origins`
- `origin_policy_mode`

The origin policy should support at least:

- explicit allowlist
- disabled/no-browser mode

### Operational Status

Required:

- `status`

Recommended statuses:

- `active`
- `inactive`
- `quarantined`
- `pending`

### Audit Metadata

Recommended:

- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `last_reviewed_at`
- `last_reviewed_by`

## Field Semantics

### `client_code`

- Must be unique
- Must be stable once published
- Should be machine-friendly
- Should be generated by the system, not entered by operators
- Should not be used as a secret

### `project_code`

- If present on a client record for legacy compatibility, it should be generated by the system
- In the split model, the real project code lives on `realtime_projects`
- Must not be treated as the same thing as a room prefix

### `issuer_identity`

- Identifies the trust issuer or trust profile that the client uses
- May be a named issuer, signing profile, or policy label
- Should be descriptive enough for operators to understand the trust path

### `token_issuance_mode`

Recommended V1 values:

- `app_backend_signed`
- `realtime_issued_fallback`
- `manual_review`

The recommended V1 path is `app_backend_signed`.

The other values are tracking or fallback labels, not a signal that V1 should expose raw issuance secrets through the admin surface.

### `status`

Recommended V1 meaning:

- `active`: client may be used according to policy
- `inactive`: client is disabled for normal use
- `quarantined`: client is restricted due to incident or review
- `pending`: client exists but is not yet approved for live use

## Minimal Operator-Facing Form

The create/edit surface should only require:

- `name`
- `issuer_identity`
- `token_issuance_mode`
- `trusted_signing_profile`
- `status`

Everything else should be treated as advanced metadata, inherited defaults, or generated identifiers.

## Legacy Compatibility Notes

Older client rows may still carry project-policy reference columns for compatibility during the transition:

- `policy_profile_code`
- `capability_profile_code`
- `room_policy_profile_code`

New onboarding should not depend on those fields at the client root.
They belong to the project-scope model in the split design.

## Client Lifecycle

### Create

An operator or authorized admin creates the client record when a new app is onboarding.

The create flow should capture:

- client identity
- owner
- trust metadata
- origin policy
- initial status

### Review

Before activation, the client record should be reviewable for:

- naming correctness
- owner correctness
- origin list correctness
- trust metadata correctness
- project-scope assignment correctness

### Activate

Activation should move a client to `active` only when the required metadata is complete and approved.

### Disable Or Quarantine

A client may be disabled or quarantined when:

- the client is no longer in use
- an integration is under review
- a trust or policy concern exists
- incident response requires temporary cut-off

### Update

Client updates should preserve auditability.

Important changes include:

- origin list changes
- trust metadata changes
- policy reference changes
- status changes
- ownership changes

## Validation Rules

The client-management UI and backend should enforce:

- `client_code` is generated and unique
- `name` is required
- `project_code` is generated where used for legacy compatibility
- `status` must be one of the supported statuses
- `token_issuance_mode` must be one of the supported modes
- allowed origins must be valid URL origins
- policy references must point to existing policy records
- trust metadata must not contain raw private keys or shared secrets

## Access Rules

The client-management surface should be available only to authorized `PBB Realtime` operators/admins.

Recommended access model:

- session-authenticated browser access
- role or capability checks in the admin surface
- audit logging for create, update, status change, and disable actions

Client-management access should not be granted to app end users.

## UI Expectations

The V1 admin UI should support:

- client list
- client detail view
- create client form
- edit client form
- status change action
- disable/quarantine action
- notes and ownership display
- policy reference display

The default create/edit forms should not ask operators to type generated codes or advanced profile payloads that can be inherited from templates.

The UI should make the trust boundary obvious.

It should be clear that this is metadata and policy control, not secret storage.

## Audit Expectations

Each meaningful action should be recorded with:

- actor identity
- action type
- client code
- timestamp
- before/after values where appropriate
- reason or note when provided

Audit events should cover at least:

- create
- update
- activate
- deactivate
- quarantine
- policy reference changes
- trust metadata changes
- origin changes

## Failure And Safety Considerations

The client-management surface should fail safely.

It should not:

- silently accept invalid origins
- allow duplicate client codes
- expose raw secret values
- permit untracked trust changes
- allow status changes without audit coverage

If a trust or policy reference is missing, the record should remain reviewable but should not be treated as ready for production use.

## Exit Criteria

The client-management spec is ready for implementation when:

- the client record fields are agreed
- the allowed status values are agreed
- the trust metadata model is agreed
- the origin policy model is agreed
- the role/capability model for admins is agreed
- the audit requirements are agreed

## Bottom Line

`Client Management` is the first admin-surface area because every other Realtime admin workflow depends on knowing:

- which client is being managed
- which trust metadata applies
- which origins are allowed
- which policy profile is in force
- whether the client is active, disabled, quarantined, or pending

Keep it descriptive, policy-oriented, and auditable.
Do not turn it into a secret manager.
